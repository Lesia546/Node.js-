# Definition of Done

Зміна вважається готовою, лише якщо виконано всі пункти свого рівня. Чекліст копіюється в опис PR (`.github/pull_request_template.md`). Пункт, який неможливо виконати, не викреслюється, а пояснюється в PR (що саме не виконано і чому).

Команди й ціль `make` для кожної перевірки: [checks.md](checks.md).

## 1. Для кожного PR

**Вимоги**

- [ ] PR посилається на розділ або AC у `spec.md`, який він реалізує або змінює.
- [ ] Якщо поведінка змінилася, спершу змінено spec (окремий коміт `docs(spec)`).

**Конвеєр**

- [ ] `make check` зелений на чистому клоні (`npm ci && make check`).
- [ ] `make audit` не показує нових порушень меж модулів (після появи цілі).
- [ ] Хуки не обходилися (`--no-verify` не використовувався).

**Код**

- [ ] Модуль імпортує інший модуль лише через його `index.ts`.
- [ ] SQL лише в `src/db` або в репозиторіях, лише з параметрами.
- [ ] Нових залежностей немає, або вони обґрунтовані в PR (що замінюють, чому не вистачає Node.js/наявних пакетів).
- [ ] Немає `console.log`, закоментованого коду, `TODO` без посилання на задачу.

**Тести**

- [ ] Кожен змінений або доданий AC має тест, назва якого починається з ID (`AC-5: ...`).
- [ ] Тест падає, якщо навмисно зламати логіку (перевірено вручну або mutation-тестом).
- [ ] Тести не залежать від порядку виконання, часу й випадкових даних.

**Безпека й приватність**

- [ ] Вхідні дані перевіряються на сервері; права доступу перевіряються в кожній захищеній операції.
- [ ] У відповідях і логах немає паролів, токенів, стеків викликів, чутливих даних.
- [ ] Секрети лише у змінних середовища; `.env` не в Git, є `.env.example`.

**Історія**

- [ ] Коміти малі й осмислені (`type(scope): що і навіщо`), без «fix», «update», «wip».
- [ ] У репозиторії немає згенерованих і тимчасових файлів (`dist/`, `coverage/`, `*.log`).

## 2. Додатково, якщо зміна торкається БД

- [ ] Схема змінюється відтворюваним скриптом (міграцією), перевіреним на порожній базі.
- [ ] Обмеження цілісності (FK, UNIQUE, CHECK) задані в БД, а не лише в коді.
- [ ] Операції над кількома записами виконуються в транзакції; є тест на конкурентний сценарій, якщо він описаний у spec.
- [ ] Видалення враховує історію модерації та вимоги приватності.

## 3. Додатково, якщо ухвалено архітектурне рішення

- [ ] Є ADR у `adr/` за шаблоном `standards/adr-template.md` з розділом Confirmation.
- [ ] Confirmation реалізований перевіркою (правило лінтера, тест або ціль `make`), а не лише описаний.
- [ ] `spec.md` і `README.md` не суперечать ADR.

## 4. Для здачі завдання

- [ ] `DEFENSE.md` на одну сторінку: що і навіщо, топ-3 розбіжності з комітами, ключове рішення з посиланням на ADR, перевірка (`make check` + `/version`).
- [ ] `spec.md` ≤ 1 сторінки, критерії закомічені.
- [ ] Докази в `docs/evidence/`.

## 5. Відомі обмеження

Невиконані пункти й відомі прогалини перелічуються в PR або в `DEFENSE.md`. Приховані обмеження вважаються порушенням DoD більше за явно названі.
