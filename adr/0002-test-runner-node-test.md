# ADR-0002: Тестовий раннер — вбудований `node:test`

- Статус: accepted
- Дата: 2026-10-25
- Рішення прийняла: Плахтій Олеся (єдиний автор проекту)

## Context and Problem Statement

Для unit-, smoke- та інтеграційних тестів потрібен раннер. Думала про Vitest, а в скрипті test використовувала node --test. Який раннер обрала й зафіксувала?

## Decision Drivers

- мінімум зовнішніх залежностей (вимога NFR-04 і стандартів проєкту);
- відтворюваність: `npm ci && npm test` без додаткового налаштування;
- сумісність із TypeScript, який збирається в `dist/` через `tsc`;
- можливість пізніше додати mutation-тести та покриття;
- стабільність під Node.js LTS.

## Considered Options

- `node:test` (вбудований у Node.js)
- Vitest
- Jest

## Decision Outcome

Обрано: «`node:test`», тому що він не додає залежностей, уже працює у конвеєрі й достатній для unit-, smoke- та інтеграційних тестів на сервері. Рішення про Vitest або інший раннер можна ухвалити пізніше окремим ADR.

Тести пишуться як `tests/**/*.test.mjs` і імпортують скомпільований код із `dist/`. Тому `npm test` виконує збірку першою (`pretest`).

### Consequences

- Good: жодної додаткової dev-залежності; швидкий старт; однакова поведінка локально й у CI.
- Good: README та приведеться до фактичного стану.
- Bad: немає вбудованого watch-інтерфейсу й сніпетів Vitest, мокування простіше обмежене можливостями `node:test`.
- Bad: тести йдуть через `dist/`, тому змінений код без перезбірки не потрапить у тест (знімається `pretest`).

### Confirmation

- У `package.json` скрипт `test` дорівнює `node --test`, а `pretest` — `npm run build`.
- У `devDependencies` немає `vitest` і `jest` (планується перевірка `make audit` через `knip`).
- Кожен AC зі `spec.md` має тест, назва якого починається з його ID.

## Pros and Cons of the Options

### `node:test`

- Good: нуль залежностей, входить у Node.js LTS.
- Good: простий запуск `node --test`, вбудований звіт, підтримка `describe/it`, моків і таймерів.
- Bad: менше екосистеми, ніж у Vitest/Jest; немає готового UI.

### Vitest

- Good: зручний DX, нативна підтримка TypeScript без попередньої збірки, багата екосистема.
- Bad: додає залежності й власну конфігурацію; для поточного обсягу це надлишково.

### Jest

- Good: найпоширеніший, багато прикладів.
- Bad: важка конфігурація для TypeScript і ESM, більше залежностей, повільніший старт.

## More Information

Переглянути, якщо знадобиться запуск тестів напряму з `src/*.ts` без збірки, змінюване мокування модулів або інтеграція з mutation-інструментом, що вимагає Vitest.
