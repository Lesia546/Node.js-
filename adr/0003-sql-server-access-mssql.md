# ADR-0003: Доступ до SQL Server — клієнт `mssql` і шар `db`

- Статус: accepted
- Дата: 2026-10-25
- Рішення прийняла: Плахтій Олеся (єдиний автор проекту)

## Context and Problem Statement

Основна база даних проєкту — Microsoft SQL Server (NFR-06). Як модулі працюватимуть з нею, щоб запити були безпечними (без SQL-ін'єкцій), зміни пов'язаних записів були атомарними (заявки, імпорт), а межі модулів не розмивалися прямим доступом до таблиць?

## Decision Drivers

- безпека: лише параметризовані запити;
- керований контроль унікальності й транзакцій (AC-5, AC-9);
- мінімум залежностей і «магії»;
- можливість тестувати з реальною БД;
- повна видимість SQL для рев'ю й аудиту.

## Considered Options

- Клієнт `mssql` + власний тонкий шар `src/db` з репозиторіями
- ORM (Prisma або TypeORM)
- Query builder (Knex)

## Decision Outcome

Обрано: «`mssql` + тонкий шар `src/db`», тому що SQL лишається явним, параметризація обов'язкова за конструкцією, а транзакції й унікальні індекси застосовуються безпосередньо та перевіряються тестами.

Правила:

1. Лише `src/db` імпортує `mssql`. Решта модулів отримує доступ через функції/репозиторії.
2. Запити пишуться з параметрами (`request.input(...)`); конкатенація користувацького вводу заборонена.
3. Рядок підключення береться зі змінних середовища; у репозиторії лише `.env.example`.
4. Схема змінюється відтворюваними SQL-міграціями в `db/migrations/`.
5. Унікальність і зв'язки задаються в БД: `UNIQUE(sourceId, externalId)`, унікальна активна заявка `(publicationId, userId)`, зовнішні ключі.

### Consequences

- Good: SQL видно в рев'ю; немає прихованих запитів і N+1 з ORM.
- Good: прямий контроль транзакцій і рівнів ізоляції для сценаріїв із гонками (заявки, імпорт).
- Good: одна зовнішня залежність у шарі даних.
- Bad: більше ручного коду (мапінг рядків у типи, міграції).
- Bad: типобезпека результатів запитів забезпечується вручну (схеми валідації на виході).

### Confirmation

- Правило ESLint `no-restricted-imports` забороняє імпорт `mssql` поза `src/db/**`.
- `dependency-cruiser` (`make audit`) забороняє залежність модулів від `src/db` в обхід його публічного інтерфейсу.
- Інтеграційний тест AC-5 запускає дві паралельні заявки одного користувача й очікує одну активну.
- Тест або перевірка в CI, що в репозиторії немає файлів `.env` і рядків підключення з паролем.

## Pros and Cons of the Options

### `mssql` + `src/db`

- Good: явний параметризований SQL, мінімум залежностей, повний контроль над транзакціями.
- Good: просто відтворити схему (SQL-скрипти).
- Bad: більше ручної роботи й дисципліни від розробника.

### ORM (Prisma / TypeORM)

- Good: типобезпечні моделі, автоматичні міграції, менше шаблонного коду.
- Bad: велика залежність і генерація коду; прихований SQL ускладнює аудит; особливості SQL Server (індекси з фільтром, ізоляція) складніше контролювати.

### Query builder (Knex)

- Good: компонований SQL, міграції, захист від ін'єкцій за замовчуванням.
- Bad: додаткова абстракція над SQL, яку треба вивчати; підтримка SQL Server залежить від драйвера, тож `mssql`/`tedious` усе одно потрібен.
